# Model selection and acceptance

Default to `gpt-5.6-luna` / `medium` with coordinator review. Use `low` only for mechanical collection from an explicit, already validated operation ledger. If one focused correction cannot resolve source/async/cache or trace attribution, coordinator investigates; `gpt-5.6-terra` / `medium` is an optional, untested escalation. Neither Luna effort in the pilot qualified for unattended performance audits.

The September 2026 frozen Keymap production-preview pilot gave both Luna efforts the same Demo edit → Save → application Reload → restore journey. Both completed functional readback. Low initially misread Save as a reload and mixed interaction groups; medium traced more correctly but used tool wall time for repeated cycles. Neither delivered complete operation-specific latency and async completion samples. The trial had one worker per effort and unequal review guidance, so it establishes no general reliability or cost ranking. Token use was unavailable; do not infer cost from elapsed time. Check [current pricing](https://developers.openai.com/codex/pricing) for budget decisions.

Before repetitions, inspect one valid sample: label, real control, page-clock window, nonzero interaction ID, duration, and end state. Correct tool-time or combined-stream reports before continuing. Verify source claims in exact handlers and awaited callees; map a trace interaction to its control before attribution. Accept functional readback, immediate response, async completion, and resources separately. A missing dimension prevents a complete audit, even when other evidence is valid.

For a future model comparison, freeze skill/prompt, fixture, build/browser, and metrics; serialize timing in isolated processes. Record queue/active time, retries, review interventions, valid samples, cleanup, and actual tokens. Repeat before generalizing or scheduling unattended use.
