# 仕様作成・更新標準

状態: v1。キーマップの実作成と低コスト agent による探索を通じて改訂済み。今後も再利用できる知見はこの標準へ、未解決の仕様差分は対象ページへ反映する。試行ごとの生ログは HEAD に蓄積しない。

## 小さな作成例

不足: 「Save で保存できる。エラー時は通知する」。これでは押しただけで pass にでき、保存先も再試行方法も分からない。

必要な記述: 「dirty 状態で Save → 成功応答後 `Saved`、Save 無効。ページの Reload 後も選択値を維持。デバイス RAM から flash へ保存。RPC 失敗はページ alert に表示し約 5 秒で消えるが、消失は成功の証拠ではない。Demo で確認できるのは擬似デバイスの再読込まで」。根拠は `useKeymap.saveChanges` とし、実機電源断後の確認は別行の未検証にする。

## 完了条件

別の agent がコードを読まず、入口と前提を整えて代表フローを実行できること。期待結果は見える文言・選択・有効/無効・保存後の再読込などで判定できること。コードを読めば同じ根拠へ辿れること。

## 作成手順

1. `src/App.tsx`、対象ページ、呼ばれる hooks / components、対応テストを読む。主画面だけでなくダイアログ、メニュー、空・読込中・未対応・ロック・エラーを列挙する。
2. 操作一覧を作る。各操作について入力、条件、状態変化、副作用、永続化、失敗経路を handler から hook まで追う。コメントだけで保証しない。依存パッケージ内で不明なら不明と記載する。
3. [テンプレート](TEMPLATE.md) を複製し、各項目を埋める。該当しない節も「該当なし + 理由」を残す。未確認を空欄や「通常どおり」で隠さない。
4. 要求に出典を付ける。明示要求（設計文書・issue 等）、実装からの推定、提案を区別する。推定要求は製品側の承認済み要件ではない。
5. 一つの仕様 ID には一つの判定可能な約束を書く。`KM-001` 等の機能固有 prefix + 番号を使い、改番・再利用しない。削除時は廃止と移転先を残す。
6. 代表フローに仕様 ID を添える。初期値を記録し、成功・キャンセル・境界・失敗/復帰を含める。初期値が変動する場合は固定値を仮定しない。
7. ソースと仕様を逆向きに照合する。全ての主要操作・表示条件が仕様のどこにあるか確認する。共有契約はモジュール仕様へ分離し、ページには固有条件とリンクを残す。
8. レビューと UI テストの実施範囲・未検証を記録する。画面未確認なのに「確認済み」と記載しない。

## 必須の粒度と証拠

- 機能要求と現行仕様を別節にする。現行に問題があれば両者の差分を未解決事項へ書く。
- ソース根拠はリポジトリ相対リンクと symbol 名。変動しやすい行番号だけに依存しない。主要な仕様行は根拠 ID を持つ。
- 状態を最低限、未接続・loading・ready・empty・unsupported・locked・dirty・saving・error の観点で点検する。存在しない状態は理由を述べる。
- 保存先は browser localStorage / IndexedDB / デバイス RAM / デバイス flash / 外部サービスを区別する。「保存」で一括しない。
- 「エラーを表示」だけでは不足。どこに何を表示し、入力とダイアログが残るか、再試行手段、自動消去の有無を書く。不明なら未確認と明示する。
- Close / Escape / 外側クリック / Cancel / 親画面切替は別々に handler を追う。「閉じる = 取消」と仮定しない。共有 component は caller と内部の双方を読み、presentation ごとの適用条件を表にする。
- `disabled` の条件を「有効条件」へ訳すときは論理を反転して確認する。例: `disabled={!dirty || loading}` なら有効条件は `dirty && !loading`。否定や AND/OR を文章化した後、clean/dirty/loading の具体例で逆転がないか点検する。
- 「接続なしで表示できる」と「connection provider を mount しない」は別。ユーザーに見える gate と内部の起動条件を混同しない。
- 表示の基準データと書込み対象を区別する。中央側の値から作ったフォームでも RPC が全デバイスへ適用する場合がある。`await`、boolean 戻り値、例外の握りつぶしまで追い、コメントの「fresh read」「persistent」を実際の再読込・永続化の証明にしない。
- 不変条件は具体的な反例を持つ。例: キー A の応答が遅れても、後から選んだキー B の選択を移動させない。
- 受け入れ済み不具合は ID、範囲、症状、回避策、受け入れ根拠・担当、再評価条件を必須とする。コードに存在することや Demo 制約だけでは受け入れの根拠にならない。なければ「承認根拠を確認できたものはなし」。
- 複雑な機能は分割してよい。親ページに入口・概要・子仕様の一覧を維持し、同じ契約をコピーしない。

## 更新ルール

UI、データ保存、バリデーション、権限/対応機能、エラー、共有モジュールを変更する PR では、変更コードから関連仕様を検索し同じ PR で更新する。共有契約を変えたら全 consumer のリンクと固有条件も確認する。新しい入口は sitemap に追加する。

変更が内部リファクタリングだけなら、対応する仕様 ID と「観測可能な変更なし」の根拠を PR に書く。仕様の確認日を一括更新せず、実際に読んだ/試した範囲だけ更新する。UI テストで差分が出たら、実装修正・仕様修正・未解決への記録を判断する。現状に合わせて要求を弱めない。

## レビュー gate

`npm run spec:check` で相対リンクのファイル存在・必須節・仕様 ID の重複・Page ソースへの参照漏れを確認する。Markdown anchor、実際の route 登録、内容の正しさや操作の網羅性は保証しないため、下記の意味的レビューも必須。ページ/モジュールの必須節名はテンプレートと同じにする。

- [ ] 全入口・主要操作に仕様または明示的な未確認がある。
- [ ] 要求の出典、現行実装の根拠、UI 実測が区別されている。
- [ ] 初見の agent が前提・操作・期待結果・復帰方法を特定できる。
- [ ] 永続化と destructive 操作、境界、非同期、エラーを点検した。
- [ ] 共有契約の重複とリンク切れがなく、変更の影響先が辿れる。
- [ ] 受け入れ済み不具合を勝手に増やしていない。
- [ ] 未検証・到達不能を pass にしていない。

## 作成 agent への依頼ひな形

```text
対象: <route / Page component> と呼ばれる hooks/components/tests。
出力: docs/spec/pages/<name>.md（共有契約が必要なら指定の modules/<name>.md）。
AGENTS.md → docs/spec/README.md → AUTHORING.md → TEMPLATE.md を読む。
全主要操作を列挙して handler→hook の成功/失敗/保存先を追う。
テンプレートの全節を保ち、要求の推定と現行実装、UI実測を分離する。
出典は実在する相対リンク+symbol。空欄や想像で埋めず不明点を明示する。
担当ファイルだけ編集し、他担当の共有契約はリンクで参照する。
spec:check、リンク確認、操作一覧から仕様への逆照合を実行。
完了報告には担当入口、仕様ID範囲、根拠、未確認、共有契約の影響先を含める。
```

worker の報告だけで完了としない。reviewer は少なくとも最も破壊的な操作、保存境界、終了/取消、未対応、失敗経路をコードと照合する。見つけた誤りを個別ファイルだけでなく標準・テンプレートの改善に反映する。
